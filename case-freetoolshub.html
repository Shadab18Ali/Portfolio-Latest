Overview

A utility site where trust matters as much as features.

People use tools like these with personal documents: photos for application forms, signed PDFs, scanned pages. FreeToolsHub keeps all of that on the visitor's device. I built the app, the tools, the content and the SEO, and deployed it on Cloudflare with its own domain.

The Challenge

  • Private by design. Uploading a passport photo or a signed form to an unknown server is a real risk, so no file could leave the device.
  • Heavy work in a browser tab. Text recognition, PDF editing, HEIC decoding and background removal usually need a server. Here they had to run on the client without blocking the main interface.
  • A growing catalogue without repeating the work. Every tool needs its own page, instructions, FAQs and metadata, and they all had to stay consistent.

Constraints

  • Zero running cost. No paid APIs or databases, so the site is a static export hosted on Cloudflare.
  • Honest content only. No invented reviews, ratings or statistics, and the privacy policy has to describe what the site really does.
  • Consent first. Analytics and ads stay off until the visitor accepts and real IDs exist, and third-party scripts load only after consent.
  • Nothing the visitor types is executed. User-supplied HTML, CSS and code is treated as text, never rendered or run.

My Role

I designed and built it end to end: the Next.js app, every tool component and the shared PDF and image logic, the brand and layout, the blog, technical SEO and the Cloudflare deployment.

What I Built

  • 93 tools listed on the current homepage: the catalogue spans PDF, image, calculator, developer, text and SEO utilities. The homepage screenshot shows the current count.
  • A registry-driven site. One typed entry per tool drives its page, metadata, FAQs, related links and search, and content tests fail the build if titles, descriptions or links are wrong.
  • Technical SEO. Metadata, canonical URLs, Open Graph, JSON-LD and an XML sitemap, plus a post-build check that fails on overlong or duplicate titles and descriptions.
  • 20+ original how-to guides that sit next to the tools and link into them.
  • Consent-gated analytics. Google Analytics loads only after the visitor accepts, and records which tool was used, never file names or contents.

How a File Is Handled

Choose a file

The browser reads the file straight from the visitor's device. Nothing is sent anywhere.

Process on the device

The tool's code loads on demand and runs locally. Heavy work, such as text recognition, runs in a Web Worker so the page stays responsive.

Download the result

The result is built in memory and saved from the browser. The site never holds a copy.

The Hard Part

Heavy engines without a heavy site. Text recognition, HEIC decoding and background removal depend on large WebAssembly engines. Shipping them with every page would slow down someone who just wants a word counter. So each tool is its own lazy-loaded chunk, and the heavy engines load only when that tool is used, from the site's own origin instead of a CDN. A build script copies them out of the npm packages, so nothing third-party is fetched at runtime.

The other trap was stale results: if someone swaps the file mid-read, the old run must not overwrite the new one. Each run carries a token, and the worker is terminated as soon as it finishes.

Simplified from the text recognition tool, not the full component

// The OCR engine (WebAssembly) loads only when someone presses "Read text"
const { createWorker } = await import("tesseract.js");

// Engine and language data come from the site itself, not a third-party CDN
const worker = await createWorker(language, 1, {
  workerPath: `${origin}/ocr/worker.min.js`,
  corePath:   `${origin}/ocr/core`,
  langPath:   `${origin}/ocr/lang`,
});

// Runs in a Web Worker, so the page stays responsive
const result = await worker.recognize(canvas);
await worker.terminate();

Takeaway

Constraints shaped the design. Ruling out a backend removed storage, accounts and privacy risk in one decision and pushed the effort into careful client-side engineering. The same approach carries over to storefronts: ship less JavaScript and load heavy features only when a visitor asks for them.
